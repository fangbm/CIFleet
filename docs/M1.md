# M1: Real Linux node control

M1 connects a CIFleet controller (intended for the Raspberry Pi) to a Linux x86_64 Docker worker (the E5 host).

## What M1 implements

- TLS 1.3 mutual authentication between controller and agents.
- Agent certificate identity binding: the client certificate Common Name must equal the heartbeat `node_id`.
- Periodic heartbeats with OS, architecture, capabilities and Docker capacity.
- Node liveness TTL; stale nodes remain visible but are marked offline and excluded from scheduling.
- Docker instance create/destroy endpoints on the agent.
- Repository-scoped persistent cache directories.
- CPU and memory reservations for scheduling.
- Per-job deadline labels plus periodic orphan/timeout cleanup that survives agent restarts.

GitHub webhook/JIT runner integration is intentionally M2. M1 proves that the secure control plane and Linux execution substrate work first.

## 1. Build

On both Linux machines:

```bash
go build -o cifleet-controller ./cmd/controller
go build -o cifleet-agent ./cmd/agent
```

Install the appropriate binary under `/usr/local/bin`.

## 2. Create a small local PKI

Run this once on a trusted machine. Replace hostnames with names or IPs actually reachable on your LAN:

```bash
./scripts/gen-dev-pki.sh ./pki pi-controller.lan e5 e5.lan
```

Copy only these files to the Raspberry Pi controller:

```text
ca.crt
controller.crt
controller.key
```

Copy only these files to the E5 worker:

```text
ca.crt
e5.crt
e5.key
```

Do **not** copy `ca.key` to either runtime node. Keep it offline for issuing/revoking replacement certificates.

The agent certificate CN is `e5`. `CIFLEET_NODE_ID` must therefore also be `e5`. The controller rejects a heartbeat if these differ.

## 3. Raspberry Pi controller

Create `/etc/cifleet/controller.env` from `configs/controller.env.example`, place certificates under `/etc/cifleet/pki`, then:

```bash
sudo cp deploy/systemd/cifleet-controller.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now cifleet-controller
sudo journalctl -u cifleet-controller -f
```

By default the API listens on `:8080` and requires a trusted client certificate for every HTTPS connection.

## 4. E5 Docker worker

Docker must already work on the host. Create `/etc/cifleet/agent.env` from `configs/agent.env.example`, then create the cache root:

```bash
sudo install -d -m 0750 /var/lib/cifleet/cache
sudo cp deploy/systemd/cifleet-agent.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now cifleet-agent
sudo journalctl -u cifleet-agent -f
```

A successful heartbeat causes the controller to expose the E5 node through `GET /v1/nodes`.

## 5. Verify mTLS and heartbeat

From the E5 host, using its certificate:

```bash
curl --cacert /etc/cifleet/pki/ca.crt \
  --cert /etc/cifleet/pki/e5.crt \
  --key /etc/cifleet/pki/e5.key \
  https://pi-controller.lan:8080/v1/nodes
```

Expected shape:

```json
[
  {
    "id": "e5",
    "os": "linux",
    "arch": "amd64",
    "backends": ["docker"],
    "online": true,
    "capacity": {
      "total_cpu": 12,
      "free_cpu": 12,
      "running_jobs": 0
    }
  }
]
```

CPU count varies by host/VM configuration.

## 6. Smoke-test a Docker instance

The agent API itself also requires mTLS. A controller certificate can be used for the M1 smoke test:

```bash
curl --cacert ./pki/ca.crt \
  --cert ./pki/controller.crt \
  --key ./pki/controller.key \
  -H 'content-type: application/json' \
  -d '{
    "id":"smoke-1",
    "repository":"fangbm/CIFleet",
    "image":"ubuntu:24.04",
    "command":["sleep","300"],
    "cpu":1,
    "memory_mb":256,
    "timeout_seconds":600,
    "cache_mounts":[{"name":"smoke","target":"/cache"}]
  }' \
  https://e5.lan:8090/v1/instances
```

The created container receives `io.cifleet.*` labels. Its cache is stored under a repository hash below `/var/lib/cifleet/cache`, so two repositories cannot accidentally share the same cache namespace.

Delete it with:

```bash
curl --cacert ./pki/ca.crt \
  --cert ./pki/controller.crt \
  --key ./pki/controller.key \
  -X DELETE https://e5.lan:8090/v1/instances/<container-id>
```

If it is not explicitly deleted, the agent janitor removes it after its deadline. Because the deadline lives in a Docker label, cleanup still works after an agent restart.

## Development-only plaintext mode

Both binaries expose `-insecure-http` for localhost development. Do not use it for worker traffic on a LAN or over the internet.

## M1 security boundary

A process with access to the Docker daemon is effectively privileged on the host. The agent therefore treats Docker access as a trusted host capability. Public/untrusted pull requests must not be routed to these workers until the M2/M4 trust policy is implemented.
