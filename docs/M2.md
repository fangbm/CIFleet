# M2: GitHub Actions JIT runners

M2 connects GitHub Actions to the M1 control plane. A `workflow_job: queued` webhook is verified by the controller, persisted as pending work, matched to an eligible worker, and converted into a GitHub JIT runner. The E5 agent launches that runner in an ephemeral Docker container. A `completed` webhook destroys the container and leaves only repository-scoped cache data.

## Data flow

```text
GitHub Actions
  | workflow_job webhook (HTTPS + HMAC-SHA256)
  v
CIFleet controller :8081 (loopback behind reverse proxy)
  | trust check + scheduler + GitHub App/JIT API
  | mTLS
  v
E5 agent :8090
  |
  v
Docker: ghcr.io/actions/actions-runner
  | exactly one JIT job
  v
container removed
```

The M1 control API remains separate on `:8080` and requires mTLS. The webhook listener defaults to `127.0.0.1:8081` and is intended to sit behind an HTTPS reverse proxy or tunnel.

## 1. Create a GitHub App

In GitHub, create a GitHub App for CIFleet. For the first test, install it only on `fangbm/CIFleet`.

Configure these repository permissions:

- **Actions: Read-only** — needed for `workflow_job` context and workflow-run trust checks.
- **Administration: Read & write** — needed to create/delete repository self-hosted JIT runners.

Subscribe to the **Workflow job** webhook event.

Set the webhook URL to your public HTTPS endpoint, for example:

```text
https://ci.example.com/github/webhook
```

Generate a high-entropy webhook secret and configure the same value in both GitHub and CIFleet:

```bash
openssl rand -hex 32
```

Download one GitHub App private key. Keep it on the controller only.

For `CIFLEET_GITHUB_APP_ISSUER`, use the App **Client ID**. GitHub also accepts the numeric App ID as the JWT issuer, but Client ID is the preferred value in current GitHub documentation.

## 2. Install controller secrets

On the Raspberry Pi:

```bash
sudo install -d -o cifleet -g cifleet -m 0750 /etc/cifleet/github
sudo install -o cifleet -g cifleet -m 0600 app.pem /etc/cifleet/github/app.pem
printf '%s\n' 'YOUR_WEBHOOK_SECRET' | sudo tee /etc/cifleet/github/webhook-secret >/dev/null
sudo chown cifleet:cifleet /etc/cifleet/github/webhook-secret
sudo chmod 0600 /etc/cifleet/github/webhook-secret
```

Copy `configs/controller.env.example` to `/etc/cifleet/controller.env` and set at least:

```ini
CIFLEET_GITHUB_APP_ISSUER=Iv1.your-client-id
CIFLEET_GITHUB_APP_PRIVATE_KEY_FILE=/etc/cifleet/github/app.pem
CIFLEET_GITHUB_WEBHOOK_SECRET_FILE=/etc/cifleet/github/webhook-secret
CIFLEET_WEBHOOK_LISTEN=127.0.0.1:8081
```

Keep the existing M1 mTLS settings unchanged.

## 3. Publish only the webhook endpoint

Terminate public TLS before CIFleet. For example with Caddy:

```caddyfile
ci.example.com {
    reverse_proxy /github/webhook 127.0.0.1:8081
}
```

Do not expose the M1 `:8080` control plane as a public unauthenticated endpoint. It remains mTLS-only.

If you use Cloudflare Tunnel or another reverse tunnel, point only the public webhook hostname/path to `http://127.0.0.1:8081`.

## 4. Upgrade both binaries

On the Pi and E5, update the repository and rebuild the appropriate binary:

```bash
git pull
go build -o cifleet-controller ./cmd/controller
go build -o cifleet-agent ./cmd/agent
```

Install the controller on the Pi and the agent on the E5 under `/usr/local/bin`, then restart the services:

```bash
sudo systemctl restart cifleet-controller
sudo systemctl restart cifleet-agent
```

The E5 agent now restricts worker control endpoints to a client certificate whose CN matches `CIFLEET_CONTROLLER_IDENTITY` (default `controller`).

Pre-pull the official runner image on the E5 so the first job does not wait on a large image pull:

```bash
sudo docker pull ghcr.io/actions/actions-runner:latest
```

## 5. Run the smoke workflow

M2 adds `.github/workflows/cifleet-smoke.yml`:

```yaml
runs-on: [self-hosted, cifleet, linux-x64]
```

In GitHub, open **Actions -> CIFleet Smoke -> Run workflow**.

Expected lifecycle:

1. GitHub sends `workflow_job: queued`.
2. CIFleet validates the HMAC signature and trust policy.
3. The job is persisted as `pending` before provisioning.
4. The scheduler selects the E5 Docker worker.
5. CIFleet creates a repository-scoped JIT runner through the GitHub App installation.
6. The controller sends only the short-lived JIT configuration to the E5 over mTLS.
7. The E5 launches `ghcr.io/actions/actions-runner` and the job starts.
8. GitHub sends `workflow_job: completed` and CIFleet removes the container/runner record.

Useful logs:

```bash
# Pi
sudo journalctl -u cifleet-controller -f

# E5
sudo journalctl -u cifleet-agent -f
sudo docker ps -a --filter label=io.cifleet.managed=true
```

The smoke job should print `CIFleet JIT runner OK` and its runner name should begin with `cifleet-`.

## Trust policy

M2 deliberately refuses dangerous public-repository cases before creating a runner:

- public fork `pull_request` jobs are rejected;
- public `pull_request_target` jobs are rejected;
- private repository jobs are allowed;
- other public-repository events can run only when the workflow explicitly requests the `cifleet` label.

This is a baseline policy, not a complete sandbox for arbitrary hostile code. Do not relax it casually.

## Reliability and idempotency

Webhook delivery is at-least-once, so CIFleet does not treat a delivery as a one-shot command. M2 stores job state in `CIFLEET_STATE_FILE`:

- queued work is persisted before provisioning;
- jobs stay pending when a worker is offline or lacks capacity;
- the controller periodically retries pending work;
- duplicate queued deliveries do not create a second runner;
- completed/rejected tombstones are retained temporarily to absorb redelivery;
- a restarted controller reloads pending/running state from disk.

The Docker backend also retains its independent deadline-label janitor from M1.

## Labels

The marker label is `cifleet` by default. M2 understands these placement labels:

```text
linux-x64
linux-arm64
windows-x64       # modelled, not launched by M2 yet
macos-arm64       # reserved for future support
cifleet-vm        # requests VM isolation; no M2 VM launcher yet
cifleet-cap-NAME  # requires worker capability NAME
```

A normal M2 Linux job should use:

```yaml
runs-on: [self-hosted, cifleet, linux-x64]
```

## Current limitations

- M2 launches Docker-backed Linux JIT runners only. KVM, Hyper-V and macOS launchers remain later milestones.
- The official Actions runner image is intentionally minimal and is not equivalent to GitHub's `ubuntu-latest` image. Workflows must install their own toolchains or CIFleet should later provide curated runner images.
- The runner container is not given `/var/run/docker.sock`. Docker-in-Docker, service containers, and workflows that require host Docker need a future rootless-Docker/KVM policy instead of silently granting host-root-equivalent access.
- Automatic GitHub-hosted -> CIFleet quota switching is M4.
